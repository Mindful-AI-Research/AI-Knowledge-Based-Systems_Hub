O terminal: Ghostty + zsh + Oh My Zsh

setup · 4 min

Instalar o Ghostty (Linux)

Terminal moderno, GPU-accelerated, do Mitchell Hashimoto. Baixe em ghostty.org.

instalar ghostty
# Ubuntu/Debian — via snap (mais simples)
sudo snap install ghostty --classic

# Arch
sudo pacman -S ghostty

Config do Ghostty (espaçamento + fonte)

Arquivo: ~/.config/ghostty/config. É aqui que vem o respiro visual.

~/.config/ghostty/config
font-family = JetBrainsMono Nerd Font
font-size = 15
window-padding-x = 14
window-padding-y = 12
background-opacity = 0.96
theme = catppuccin-mocha
cursor-style = block
mouse-hide-while-typing = true

zsh + Oh My Zsh

zsh + omz
# 1. instalar e tornar padrão
sudo apt install zsh -y
chsh -s $(which zsh)

# 2. Oh My Zsh
sh -c "$(curl -fsSL https://raw.githubusercontent.com/ohmyzsh/ohmyzsh/master/tools/install.sh)"

Tema Powerlevel10k — o wizard de onboarding

É o p10k configure que dá ícones, segmentos, two-line e espaçamento. Esse é "aquele comando de config".

powerlevel10k
git clone --depth=1 https://github.com/romkatv/powerlevel10k.git \
  ${ZSH_CUSTOM:-$HOME/.oh-my-zsh/custom}/themes/powerlevel10k

# no ~/.zshrc trocar a linha do tema por:
# ZSH_THEME="powerlevel10k/powerlevel10k"

# rodar o wizard (escolhe ícones, espaçamento, prompt de 2 linhas, etc)
p10k configure

Plugins que mudam o jogo

autosuggestions + syntax highlight
git clone https://github.com/zsh-users/zsh-autosuggestions \
  ${ZSH_CUSTOM:-~/.oh-my-zsh/custom}/plugins/zsh-autosuggestions
git clone https://github.com/zsh-users/zsh-syntax-highlighting \
  ${ZSH_CUSTOM:-~/.oh-my-zsh/custom}/plugins/zsh-syntax-highlighting

# no ~/.zshrc:
# plugins=(git zsh-autosuggestions zsh-syntax-highlighting)

Memória entre sessões — ai-memory (Akita)

killer feature · 6 min

1. Instalar o ai-memory (binário, sem Docker)

binário via release
cd /tmp
curl -fsSL -O https://github.com/akitaonrails/ai-memory/releases/download/v1.4.1/ai-memory-linux-x86_64.tar.gz
tar -xzf ai-memory-linux-x86_64.tar.gz
install -m 755 ai-memory ~/.local/bin/

Vai pro ~/.local/bin/ — garanta que está no PATH. Sem Docker, sem rust.

2. Ligar o servidor (local, com token) — deixa rodando num painel

init + serve
ai-memory init
ai-memory generate-auth-token > ~/.local/share/ai-memory/.demo_token

AI_MEMORY_AUTH_TOKEN=$(cat ~/.local/share/ai-memory/.demo_token) \
  ai-memory serve --transport http --bind 127.0.0.1:49374

Esse painel fica ocupado servindo. Abra outro split (Ctrl+Shift+D) pro próximo passo.

3. Plugar no repositório (noutro painel)

install per-repo + opencode
cd ~/Desktop/AgentSmith/agent-smith-v6-deploy
TOKEN=$(cat ~/.local/share/ai-memory/.demo_token)

# Claude Code — escopo do projeto (.mcp.json no repo)
ai-memory install-mcp --client claude-code --apply \
  --config-file ./.mcp.json \
  --server-url http://127.0.0.1:49374/mcp \
  --auth-token "$TOKEN"

# opencode — config global
ai-memory install-mcp --client open-code --apply \
  --server-url http://127.0.0.1:49374/mcp \
  --auth-token "$TOKEN"

# segurança: o token fica inline no .mcp.json → NÃO commita
echo ".mcp.json" >> .gitignore
O token vai inline no .mcp.json. O echo ".mcp.json" >> .gitignore é obrigatório — senão vaza credencial no commit. Note o /mcp no fim da URL e o client open-code (com hífen).

4. MCP vs Hooks — o que eu escolhi (e por quê)

MCP  install-mcpmemória sob comando (manual)eu uso
Hooks  install-hookscaptura automática (toda sessão)não uso

Injetar agentes no repositório sob comando

ideia top · 5 min
✓ Montado: biblioteca + skill /migrate-agents. Sugerir agentes pela stack é uma skill custom (não nativa) — nativo é só o Claude ler .claude/agents/.

Como funciona

Subagents não são compartilhados como skills — cada harness lê da sua pasta: .claude/agents/ (Claude) · .opencode/agents/ (OpenCode) · Codex (camada [agents]) · Kimi (YAML). Cada agente é um .md com frontmatter (name, description, tools, model).

1. Clonar a biblioteca de agentes

biblioteca
git clone https://github.com/VoltAgent/awesome-claude-code-subagents.git ~/.agents-library
# 154 agentes prontos em ~/.agents-library/categories/01..10
# dev, infra, data/ai — testes/QA em 04-quality-security

2. A skill migrate-agents (sugere pela stack)

~/.claude/skills/migrate-agents/SKILL.md
---
name: migrate-agents
description: Detecta a stack do projeto, sugere ate 5 subagents de dev + 1-2 de teste da biblioteca ~/.agents-library e instala os escolhidos na pasta de agents do harness.
trigger: /migrate-agents
---
1. Detecte a stack (package.json, requirements.txt, go.mod...).
2. Leia ~/.agents-library/categories/ e case os agentes com a stack.
3. Sugira ate 5 de DEV + 1-2 de TESTE, com o porque. NAO instale ainda.
4. Apos o usuario confirmar, copie os .md escolhidos para a pasta de
   agents do harness atual (.claude/agents/, .opencode/agents/...).

3. Rodar — detecta, sugere, instala

no claude / codex / kimi
/migrate-agents
# le a stack, sugere 5 dev + 1-2 teste, voce confirma,
# e instala em .claude/agents/ (ou a pasta do harness)

4. AGENTS.md ensina os harnesses a usar

~/.codex/AGENTS.md (herdado por todos)
## Subagentes especialistas do repositorio
Se o repo tiver .claude/agents/ (ou .opencode/agents/), PREFIRA delegar a
esses subagentes quando a tarefa bater com a especialidade deles.
Para popula-los pela stack, use a skill migrate-agents (/migrate-agents).

Playwright automático em /loop (play→write→test→report)

poderoso · 6 min

1. Instalar Playwright

playwright
npm init playwright@latest
# instala o runner + browsers + reporter HTML built-in

2. Criar o slash command que recebe a spec por argumento

Arquivo ~/.claude/commands/e2e-from-spec.md (global — vale em todo projeto) — vira o comando /e2e-from-spec. O $ARGUMENTS é o nome da spec que você passa na hora de chamar, então o mesmo comando serve pra qualquer spec.

~/.claude/commands/e2e-from-spec.md
Leia o arquivo de spec: $ARGUMENTS
Para cada critério de aceite dessa spec:
1. gere/atualize um teste Playwright em tests/
2. rode: npx playwright test --reporter=html
3. se algum teste falhar, conserte o código e rode de novo
4. ao final, o relatório fica em playwright-report/index.html
Resuma quantos passaram/falharam.

3. Rodar — o /loop faz parte do comando

O /loop precisa envelopar o comando. Sem ele, o agente roda uma vez e para no meio do ciclo play→write→test. Com o loop, ele repassa a spec e regenera/roda sozinho até fechar.

dentro do claude code
# /loop INTERVALO /comando ARGUMENTO-DA-SPEC
/loop 15m /e2e-from-spec SPEC.md

# o HTML de resultado já vem pronto:
# playwright-report/index.html
O /loop é skill nativa do Claude Code. Troque SPEC.md pelo nome real do seu arquivo de spec.

Workflow como skill

avançado · 5 min

1. Criar a skill workflow-codex

Salve o orquestrador como uma skill em ~/.codex/skills/workflow-codex/SKILL.md e ~/.claude/skills/workflow-codex/SKILL.md — assim vale em Claude, Codex, Kimi e OpenCode. O frontmatter precisa de name e description — a description é o que dispara a skill quando você descreve a tarefa. A spec vai em linguagem natural na hora de chamar (skills não usam $ARGUMENTS).

~/.codex/skills/workflow-codex/SKILL.md (+ ~/.claude/skills/)
---
name: workflow-codex
description: Orquestra um pipeline de desenvolvimento dirigido por spec, com plano de sprints, validação adversarial, refuter, desenvolvimento isolado por sprint e gate final. Use quando o usuário pedir para rodar uma spec de ponta a ponta.
---

Você é o orquestrador de um pipeline de desenvolvimento
dirigido por spec. A spec alvo é a que o usuário indicou.

FASE 1 — PLANO DE SPRINTS
Leia a spec por inteiro. Quebre-a em sprints e,
dentro de cada sprint, referencie explicitamente as seções
da spec que aquela sprint cobre.

FASE 2 — VALIDAÇÃO ADVERSARIAL DO PLANO
Lance 3 validadores adversariais independentes para auditar
as sprints: cobertura da spec, dependências entre sprints e
critérios de aceite verificáveis.

FASE 3 — REFUTER
Lance 1 refuter para checar se os achados dos 3 adversariais
procedem de fato (só evidência reproduzível conta). Descarte
o que for ruído.

FASE 4 — CORREÇÃO DO PLANO (loop, máx. 2x)
Devolva os achados procedentes ao agente que escreveu as
sprints para corrigir. Repita as fases 2 a 4 no máximo 2 vezes.

FASE 5 — DESENVOLVIMENTO
Lance um desenvolvedor por sprint. Cada um recebe SOMENTE o
contexto da sua sprint e as seções da spec referenciadas nela.
Nada além disso.

FASE 6 — VALIDAÇÃO DA ENTREGA (loop até 100%)
Para cada entrega, lance validadores com a visão da spec e das
sprints para avaliar o trabalho do desenvolvedor. Se houver
erros, devolva ao desenvolvedor e repita até a sprint estar
100% completa.

FASE 7 — GATE FINAL
Lance 3 validadores finais para garantir que a spec foi
entregue na totalidade. Se faltar algo, devolva aos
desenvolvedores responsáveis.

2. Rodar

Você chama a skill por @ (menu de skills) ou só descrevendo a tarefa em linguagem natural — o Codex casa com a description e dispara a skill. A spec vai no próprio pedido:

no codex
@workflowcodex roda o pipeline na spec1232.md

Pra outra spec, é só apontar outro arquivo no pedido. Sem $ARGUMENTS: a spec é resolvida pelo texto que você escreve.

find-skills — descobrir e instalar skills (npx)

produtividade · 3 min

Antes de criar uma skill do zero, vale procurar no ecossistema público. O CLI npx skills (vercel-labs) busca e instala skills prontas do skills.sh. Depois de instaladas, ficam disponíveis no Codex e no Claude Code automaticamente.

1. Buscar por keyword

terminal
npx skills find "react performance"

Queries que funcionam bem: "git workflow", "pdf extract", "react performance". Prefira skills de publishers confiáveis (vercel-labs, anthropic, microsoft) com 1K+ installs.

2. Instalar globalmente

terminal
npx skills add <owner/repo@skill> -g -y

-g instala global (vale em todos os projetos), -y pula a confirmação.

3. Criar a sua própria

terminal
npx skills init

Não achou match? Faz a sua. Explore o leaderboard em https://skills.sh/ antes de criar — evita duplicar o que já existe.

pr-context — skill que carrega o git no load

coding · 3 min

Exemplo de skill que roda comandos no momento em que carrega. A sintaxe !`comando` dentro do SKILL.md executa o shell e injeta a saída no contexto — então o agente já abre com o estado do git (branch, últimos commits, diff vs base) sem precisar pedir. Ideal antes de revisar mudanças ou escrever a descrição de um PR.

1. Criar a skill

~/.claude/skills/pr-context/SKILL.md
---
name: pr-context
description: Carrega o estado atual do git (commits recentes, diff vs branch base, arquivos alterados) antes de revisar codigo ou abrir um PR. Use quando for revisar mudancas, escrever a descricao de um PR ou entender o que mudou na branch.
allowed-tools: [Bash, Read, Glob, Grep, Write, Edit]
---
Voce prepara o contexto de uma branch para revisao ou descricao de PR.

## Estado atual da branch

Branch e ultimos commits:

!`git rev-parse --abbrev-ref HEAD 2>/dev/null && echo "---" && git log --oneline -10 2>/dev/null || echo "(nao e um repo git)"`

Arquivos alterados vs a base (main ou master):

!`git diff --stat $(git merge-base HEAD main 2>/dev/null || git merge-base HEAD master 2>/dev/null || echo HEAD~1) 2>/dev/null || echo "(sem base detectada)"`

## Etapa 1 — Entender as mudancas
- Read nos arquivos do diff acima para ler o conteudo real
- Grep para rastrear quem consome o que foi alterado (impacto)

## Etapa 2 — Entregar
- Revisao: aponte bugs, riscos e quebras de contrato com arquivo:linha
- Descricao de PR: titulo + resumo + bullets do que mudou + como testar

## Regras
- NUNCA rode git que modifica estado (commit, push, reset, rebase, merge)
- Trabalhe read-only: so leitura e analise

2. Rodar

Chame por /pr-context ou descrevendo a tarefa. Os blocos !`...` rodam na hora do load, então o agente já entra com branch, commits e diff prontos.

no claude code
/pr-context revisa o que mudou nessa branch

validate-spec — validar a SPEC antes de codar

coding · 4 min

Antes de mandar um agente desenvolver uma SPEC inteira, vale provar que a SPEC bate com o código real. Esta skill lança vários agentes independentes que cruzam a SPEC com o repositório e devolvem bugs, divergências, trechos mal escritos e correções — cada achado com evidência (arquivo:linha, função, classe). A ideia é a mesma, mas a forma de invocar os agentes muda um pouco entre Claude/Codex e Kimi.

Variante A — Claude / Codex / OpenCode

Versão padrão: 3 agentes independentes numa passada só, cada um com um foco. Salve em ~/.claude/skills/validate-spec/SKILL.md (ou ~/.codex/skills/validate-spec/SKILL.md).

validate-spec · padrão
---
name: validate-spec
description: Valida uma SPEC lançando 3 agentes de IA independentes que cruzam a SPEC com o código real — apontam bugs, trechos mal escritos, divergências e correções necessárias, com evidência (arquivo:linha, função, classe). Use antes de desenvolver uma spec, para garantir que ela está correta e implementável.
trigger: /validate-spec
---

# Validate Spec — validação de SPEC por 3 agentes

Você valida uma SPEC cruzando-a com o código REAL. Lance 3 agentes
independentes de uma vez (uma passada só, sem loop), cada um com um
foco específico. Ao final, escreva um parecer embasado, referenciando
arquivos, funções, classes e linhas.

## Entrada
A SPEC alvo (nome ou caminho). Se não foi informada, pergunte.
Leia a SPEC inteira ANTES de lançar os agentes.

## Os 3 agentes (lances simultâneos, prompts específicos)

### Agente 1 — Coerência SPEC ↔ código
Abra CADA arquivo/função/classe/linha que a SPEC referencia e confirme
que existe e faz o que a SPEC afirma. Liste toda divergência (referência
inexistente, linha errada, comportamento diferente do descrito) com
arquivo:linha.

### Agente 2 — Implementabilidade e clareza da SPEC
Audite a SPEC como plano executável: fases/sprints com escopo claro?
Critérios de aceite verificáveis? Dependências corretas e completas?
Contradições internas, ambiguidades ou trechos mal escritos que
travariam um dev? Aponte a seção exata da SPEC.

### Agente 3 — Bugs e riscos no código-alvo
Olhando o código que a SPEC vai tocar, encontre bugs latentes, edge
cases, riscos (concorrência, multi-tenant, segurança, performance) e
correções necessárias ANTES de implementar. Cada achado com evidência
reproduzível (arquivo:linha, função, classe) e impacto.

## Regras dos agentes
- Cada agente lê a SPEC e o código real — não confie só na SPEC.
- Só conta achado com evidência (arquivo:linha / função / classe).
- Classifique cada achado: bloqueante / recomendado / cosmético.

## Parecer final (você consolida)
- Deduplique achados repetidos entre os 3 agentes.
- Ordene por severidade.
- Para cada ponto: o que está errado, onde (arquivo:linha/função/classe
  + seção da SPEC) e a correção sugerida.
- Veredito: a SPEC está pronta para desenvolver ou precisa de correção
  antes? Liste o que falta.

Variante B — Kimi (Agent Swarm)

No Kimi a invocação é diferente: você aciona o AGENT SWARM dele em vez de descrever "3 agentes". O foco distribuído é o mesmo. Use um nome distinto e salve em ~/.kimi-code/skills/validate-spec-swarm/SKILL.md (o home do Kimi é ~/.kimi-code, não ~/.kimi).

~/.kimi-code/skills/validate-spec-swarm/SKILL.md
---
name: validate-spec-swarm
description: Valida uma SPEC usando o AGENT SWARM do Kimi — vários agentes diferentes cruzam a SPEC com o código e devolvem falhas, bugs, trechos mal escritos e correções necessárias, com evidência (arquivo:linha, função, classe).
---

Use o AGENT SWARM com vários agentes diferentes para validar essa SPEC
e encontrar falhas ou correções necessárias para o desenvolvimento. Cada
agente do swarm assume um foco distinto e cruza a SPEC com o código REAL
do repositório — nada de validar só pela leitura da SPEC.

## Entrada
A SPEC alvo (nome ou caminho). Se não foi informada, pergunte. Leia a
SPEC inteira antes de disparar o swarm.

## Distribua o swarm em focos distintos (mínimo 3)

- Agente de coerência: abre cada arquivo/função/classe/linha referenciado
  na SPEC e confirma que existe e bate com o que a SPEC afirma; lista
  divergências com arquivo:linha.
- Agente de implementabilidade: audita a SPEC como plano — escopo das
  fases, critérios de aceite verificáveis, dependências, contradições,
  ambiguidades, trechos mal escritos; aponta a seção da SPEC.
- Agente de bugs/riscos: caça bugs latentes, edge cases e riscos
  (concorrência, multi-tenant, segurança, performance) no código-alvo,
  com correções necessárias ANTES do desenvolvimento; evidência
  reproduzível por achado.

## Regras
- Todo achado precisa de evidência (arquivo:linha / função / classe).
- Severidade por achado: bloqueante / recomendado / cosmético.

## Síntese final
Consolide os retornos do swarm num parecer embasado: dedup, ordenado por
severidade, cada ponto com o quê + onde (arquivo:linha/função/classe +
seção da SPEC) + correção, e o veredito (pronta pra desenvolver ou não,
e o que falta).

Casa direto com a seção 6: roda a validate-spec primeiro, corrige o que ela apontar, e só então solta a workflow pra desenvolver a SPEC já limpa.

Hooks (Claude Code) — automação nos eventos do agente

poderoso · 5 min

Hooks são comandos de shell que o Claude Code dispara em eventos do ciclo de vida. Ficam em .claude/settings.json (escopo do projeto) ou ~/.claude/settings.json (global), sob a chave "hooks". Cada hook recebe o contexto da tool via stdin em JSON (lido com jq).

O Codex também tem hooks (PreToolUse, PostToolUse, Stop, SessionStart…), configurados no ~/.codex/config.toml sob [hooks.*] — mesma ideia, sintaxe diferente.

1. PreToolUse — barrar comando perigoso antes de rodar

Roda antes de cada Bash. Se o comando casar com um padrão destrutivo, sai com exit 2 e o Claude Code bloqueia a execução.

.claude/settings.json · "hooks"
"PreToolUse": [
  { "matcher": "Bash",
    "hooks": [
      { "type": "command", "command": "jq -r '.tool_input.command' | grep -qE 'rm -rf /|push.*--force|mkfs|dd if=' && { echo 'Comando perigoso bloqueado pelo hook 🛡️' >&2; exit 2; } || exit 0" }
    ]}
]

2. PostToolUse — formatar o arquivo logo após editar

Roda depois de cada Edit ou Write. Pega o arquivo tocado e formata: prettier pra TS/JS/JSON, ruff pra Python.

.claude/settings.json · "hooks"
"PostToolUse": [
  { "matcher": "Edit|Write",
    "hooks": [
      { "type": "command", "command": "f=$(jq -r '.tool_input.file_path'); case \"$f\" in *.ts|*.tsx|*.js|*.json) npx prettier --write \"$f\";; *.py) ruff format \"$f\";; esac" }
    ]}
]

3. Stop — avisar quando a tarefa termina

Dispara quando o agente encerra o turno. Aqui um notify-send joga uma notificação no desktop Linux.

.claude/settings.json · "hooks"
"Stop": [
  { "hooks": [
    { "type": "command", "command": "notify-send -i dialog-information 'Claude Code' 'Terminei a tarefa ✅'" }
  ]}
]
Os três entram juntos dentro de um único objeto "hooks": { ... } no settings.json. Hook global em ~/.claude/settings.json vale pra todo projeto; no .claude/settings.json do repo, só ali.
